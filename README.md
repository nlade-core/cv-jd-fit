# cv-jd-fit

Check a CV against a job description, requirement by requirement, entirely on-device via Chrome's built-in AI. For recruiters (one JD, one CV or a folder of them) and for job hunters (one CV, one or several JDs). Nothing you add is ever sent to a server.

## Why this exists

First validation step for an on-device CV↔JD matching tool: before building real CV upload, PDF extraction, or a recruiter/candidate persona split, this answers the one question that actually mattered — is the on-device model any good at the matching itself? (v1 shipped a sample CV in the CV field; since v4 the field starts empty and the recorded example on the start page plays that role. Pasted CV text is saved to your browser's local storage only.)

**Result: yes.** Tested against two real, contrasting postings pulled live from Greenhouse and AI Dev Jobs — a backend/React/TypeScript role scored 78/100 against the sample CV's actual stack, a senior ML engineer role requiring production PyTorch/TensorFlow experience scored 30/100 against the same CV, which explicitly disclaims ML experience. The model correctly discriminated, and named the real, specific missing requirements in both cases rather than vague filler.

## What v4 adds

- **Less friction to the first result.** Hiring: the CV box starts empty (before, confirming the criteria silently ran them against a made-up sample CV), a PDF picked before confirming says results start on confirm, and the result scrolls into view when a run starts. Job hunting: "Looks right — continue" sits above the parse list as well as below it; after confirming, the list folds to its one-line summary with a "Show and fix how it was read" link, and the first JD's result scrolls into view. Recorded example: the criteria list is folded, so the result is on the first phone screen.
- **Role attachment on table-layout CVs.** A line such as "Senior BI Analyst - Own the weekly dashboard…" under a career table is matched to its role by the leading words of the role title (two or more, longest match wins), even when the table row ran title and employer together. The recorded example no longer files it under Store Manager.
- **Short prompts, always.** A criterion's routed lines are measured (`measureInputUsage` when the session has it, else ~4 characters a token). Over 600 tokens they are split between lines into chunks that repeat their section and role headers, each asked on its own clone; evidence IDs are merged with direct beating indirect. The criterion's "Searched …" line says how many parts it took; counts also go to `window.cvjdfitRouting` and the console. On the long test CV a skill criterion is ~3,800 tokens, asked as 7 prompts of at most ~2,450 characters. The budget can be tuned with `localStorage['cvjdfit.chunkTokens']`.
- **Projects & publications** is a CV section of its own (projects, publications, talks, presentations, patents, portfolio, research, open source), searched by skill, domain and leadership criteria.
- **Years you can audit.** A years criterion lists every role with its months and a checkbox. Career breaks and undated roles start unticked (undated ones stay locked until their dates are fixed in the parse check). Unticking a role — say, one outside the field — recomputes the total, the status, the highlights and the score. Saved in the project file (still version 1; the fields are additive, older files open unchanged).
- Project file names include seconds.

## What v3 adds

- **Start page.** "I'm hiring" or "I'm job hunting". The model check and session creation start on page load in the background; the click on a choice counts as the user gesture a first model download needs, so the download starts there. The download explainer lives on this page (and reappears in either mode while a download runs). The choice is remembered in this browser; the header links switch modes or go back to the start page.
- **Recorded example** ("See an example"). Replays a stored result for a sample JD and a synthetic CV: the PDF renders, then criteria and highlights land one by one. Instant, no model needed, labelled "Recorded example" throughout, read-only. **How it was produced:** `samples/recorded-example.json` is a project file saved by running this page's own pipeline headless (PDF parsing, requirement lines, routing, years in code, status rules) with a keyword-rule test stand-in in place of the on-device model. **It is not on-device model output**; it shows how the page works, not how good the model is. The replay pacing is illustrative, not measured. The CV (`samples/sample-cv.pdf`) is generated from the synthetic `syn03_partial_table` CV of the cv-evidence-bench repo; the JD (`samples/sample-jd.txt`) is made up.
- **Hiring** is the v2 flow, starting from the JD (paste or upload a .txt/.md/.pdf), then one CV or a folder batch.
- **Job hunting** starts from the CV. A parse check shows every line grouped by section and role with dates; you can move a line to another section or role, start a new role from a line, and fix a role's title and dates (years of experience are recomputed from exactly this). Then add one or several JDs (paste each, or pick several files). Criteria are extracted per JD; reviewing them is optional. Each JD gets Met / Possible / Not found with the same evidence highlighting, worded factually for the job hunter ("This JD asks for X; your CV doesn't show it", "Evidence exists … but it's weak or buried"). With several JDs a table lists them sorted by coverage. No CV rewriting, no generated advice.
- **Project files.** "Save project file" downloads one JSON file (`format: "cv-jd-fit", version: 1`) with the mode, JD(s) and criteria, parsed segments (with parse fixes), results, evidence, overrides, model availability and timestamps. The original PDFs are optional (base64, ticked by default when hiring; the resulting size is shown). Without them, an opened project shows the CV text instead of the pages. Opening restores everything, batch tables included; unknown formats and newer versions are refused with a message. The file contains personal data and lives only where you save it. This is also the fix for overrides being lost on reload.

## How v2 works (still true)

Lesson from a benchmark of a small on-device model on CV evidence: it gets much worse as prompts grow, it often answers a silent "no" with no evidence, and it is bad at met/partial/no verdicts. So prompts stay small, the model is asked only for evidence, and code decides everything else.

- **Starts early.** On load the page checks the model and creates its base sessions. On a first visit a short animated explainer shows the download progress and disappears once the model is ready. A PDF is parsed the moment it's picked. JD criteria are extracted the moment the JD is pasted (debounced), so only the matching is left once both are in.
- **Structured CV segments.** `segment.js` handles layout (columns, wrapped lines, packed skills lists into `14.1`, `14.2`, …). `structure.js` adds `{id, section, role, dates, page, boxes, text, label}`. Sections come from headings (experience / skills / education / profile / certifications / other). Experience lines get their role title and dates. Labels are built by code, e.g. "Experience › Data Scientist (2017–2021) › line 1". The model only sees a compact numbered view with section and role header lines, never the JSON.
- **JD criteria.** Code keeps the requirement sections (essential, desirable, requirements, "you'll have", …) and drops company blurb, duties, benefits and equal-opportunity text. If there are no such headings it reads the whole JD. The model turns each line into a short criterion typed skill / years / degree / domain / leadership / other, marked required or preferred; an explicit "Desirable" or "Essential" heading overrides that tag. You edit, delete, add or retype the criteria, then confirm once per role. Confirmed criteria are saved in this browser, keyed by a hash of the JD.
- **Routing, in code.** degree → education + certifications; skill → skills + experience + profile + projects; domain / leadership → experience + profile + projects; other → everything (routing to projects since v4). Each criterion is one call on a `clone()` of the base session, run sequentially, seeing only its routed lines. If a CV has none of those sections, the whole CV is used.
- **Years, in code, no model call.** Every dated role under Experience counts, except career breaks and similar, which are listed as not counted. Overlapping dates are merged, and a bare year counts January to December. The row shows each role's months and the total.
- **Status, in code.** The model returns evidence IDs tagged direct or indirect. **Met** means at least one direct line, **Possible** means indirect lines only, **Not found** means none. Years: Met if the total reaches the required number, Possible if there is some dated experience but not enough. There is never a "No". Each criterion opens to show its evidence lines with labels; clicking a line highlights it on the PDF. You can remove lines, add lines (click the CV while a criterion is open, or use the "Add a line" menu) and override the status. Overrides are marked.
- **Score.** Met 1, Possible ½, Not found 0; required criteria count double.
- **Batch.** Choose a folder (`showDirectoryPicker`) or several PDF files. CVs are checked one after another into a table of candidates × criteria with a score column, sortable by score. It shows a progress bar with an estimate of the time left, per-file parse warnings and a Stop button that keeps the rows done so far. Clicking a row opens that candidate's evidence view. Nothing is written to the folder.
- **Parse warnings.** Pages with little or no text (likely scanned) and text that looks garbled are flagged.
- **Timer and network counter.** The timer runs from "both inputs ready" and shows the time to the first result and to the last. A live counter (PerformanceObserver on resource entries) counts any request to another origin; it should stay at "0 bytes sent".

## Running it

Needs a recent desktop Chrome with the on-device model (Prompt API / `LanguageModel`) available. Serve the folder locally rather than opening `index.html` directly:

```
python3 -m http.server 8000
```

then open `http://localhost:8000`. If the status pill says "needs download", the first click or key press on the page starts the one-time download.
